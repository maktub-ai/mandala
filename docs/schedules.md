# Schedules

`/schedules` is the canonical plan directory. Existing `/tasks?rules=1` and `/mana?tab=automation` URLs retain their Project filter when redirected. Task details continue to manage their own execution rule through the same automation service.

A saved schedule is paused by default. Saving does not execute it or create an unused Task. New standalone rules default to `executionMode: independent`; rules with an explicit `taskId` default to `continuous`. Independent creates one Task and execution Chat per occurrence; continuous reuses one Task and Chat, created at first execution if no matching Chat is selected. Primary Chat cannot execute scheduled work. `goalId` is an optional coordination parent/report source, independent of execution mode. Task-origin independent rules create children of that Task. Continuous completion/cancellation pauses future triggers; independent occurrence completion leaves its schedule enabled. A completed/cancelled source Task or coordinating goal stops further work. Agent and runtime are visible choices. Selecting an Agent initializes its configured runtime, which remains editable. Changing Project, Agent or runtime clears an existing Chat target and requires a new explicit choice.

Run once requests a manual occurrence. Enabling or pausing controls future scheduled occurrences. Stopping an occurrence affects that occurrence and does not disable the schedule. Task acceptance and native Run completion are displayed separately; a successful native execution does not imply Task acceptance. Missed, unknown, approval and legacy-unverified outcomes remain visible in history. Archiving a plan retains its Task and historical occurrences.

The directory shows compact selectable summaries; the selected detail holds the goal, target Chat, workspace, management actions and that plan's history. Global history also exposes runs from archived plans. At narrow widths the detail replaces the directory and provides a return action.

Updates and archive operations use the current rule revision. A revision conflict preserves the editor's input and requires reopening the current rule before saving again. Dirty or busy editors guard navigation and browser unload.

Create and manual Run requests support an optional `Idempotency-Key`. An accepted response confirms that command before the independent directory refresh; failed refresh never turns an accepted receipt into an unknown submission. Manual Run keys are checkpointed before mutation. Desktop uses the stable native HOME preference store, separated by authenticated user identity, so stopping/restarting the runtime on another port retains the original verification key. Only identity, rule path and key are stored; no instructions, request bodies or attachments. Legacy origin-local keys migrate once for an identity, and native read/write failures block new submissions rather than generating replacement keys. Browser-only use retains origin-scoped localStorage and cannot promise recovery after clearing it or changing origin. A lost response is checked through **Check previous run** with the same key; reconnecting never sends a mutation. Create keys and unsaved schedule input remain scoped to the open editor/session. Create receipts are stored atomically with the rule in the additive `automation_create_receipts` table. The same key with a different request is rejected. Existing callers without a key remain compatible. Rollback leaves this table inert; it does not remove rules, Tasks or occurrences.

Schedules execute only while the local service is running. New rules use `missedPolicy: latest` and `overlapPolicy: coalesce`: after downtime the newest due window runs, and active work retains at most one merged pending follow-up. Explicit `each` uses `queue`; advanced `manual` catch-up remains available. Manual requests keep their own idempotency key and do not change recurrence. Weekly rules accept a nonempty unique `weekdays` array (Sunday=0); workdays is `[1,2,3,4,5]`, without holiday calendars. The old single `weekday` remains valid; dual forms must agree. Schedule association and presentation do not add remote control or configuration permissions.

Rules persisted without `executionMode` retain legacy behavior: a goal-linked rule creates one child per occurrence; a Task-linked rule shares that Task. Both create a fresh Chat unless `conversationId` was explicitly selected. Their existing missed/overlap policies and periodic Task acceptance behavior remain unchanged. Explicit mode changes apply only to future occurrences.

Each occurrence freezes its execution mode, Project, Agent, runtime, workspace and instructions, separately from the Task goal/criteria/acceptance contract. Editing work instructions affects future occurrences only. Server-owned `executionTaskId` and `executionConversationId` bindings survive restart; clients cannot set them. Mode/scope/Chat edits are rejected while pending, active or uncertain work prevents safe rebinding. Existing runs and history are retained. Generated Chat, binding and Run creation commit together.
