## Run order and evidence packet

1. Freeze the exact package and record source SHA, version, OS build and architecture, artifact SHA-256, and signature/trust result. For every row record exact vendor package version, source and resolved launcher identity (redact personal paths), bridge version, and approval/credential **mode** only. Do not copy secrets, raw sessions, or private paths into Git. Check launch on the packaged desktop, not a development shell; an already working terminal does not pass I.
2. Repeat vendor-free P and missing-launcher controls on the candidate before spending any model credits. Prove the allowlist and loopback containment before the backend starts. Use synthetic local credentials only. On Windows use an approved pre-existing disposable offline environment or equivalent pre-entry OS enforcement. Give Codex an explicit runtime fixture PATH **before first probing or sending**; ambient PATH cannot prevent registered PATH refresh. Treat unexpected PowerShell, executable, egress, or prompt as a failure; don't enable Windows Sandbox, alter registry/PowerShell policy, or run an unguarded package to get a pass. Existing test remains Mac-only; Windows mocks stay labeled source evidence.
3. For real P, in a separately approved isolated setup, stop at the checkpoint in the table. These checkpoints require no model turn but do **not** guarantee a vendor CLI won't start background services or make network requests; assume no auth/network permission during offline QA. If the checkpoint requires login, network, or unapproved provider state, stop and record the blocked boundary. Do not import from personal profiles or bypass the host's trust policy.
4. For F, use only a pre-approved vendor configuration, host, spend limit, and a disposable empty project. Disable automatic title/memory, unneeded tools/hooks/MCP, and dependent follow-up work. Send one short no-tool request in Mandala, require an attributable answer plus terminal success in the same conversation, and check the adapter did not retry, fall back, or ask for an unexpected permission. Capture only a redacted receipt and record auth or cost blockers instead of trying another provider. If vendor setup is missing, leave F blank rather than substituting a fixture result.
5. Attach the dated receipt to the release's QA item with `pass / blocked / failed / not run` for each level and OS. If a platform or runtime was not qualified, keep that limitation explicit; no summary “all supported” from a partial matrix.

Do not add a managed installer merely because the upstream documentation provides a shell script. A separate prerequisite is eligible only after a release-reviewed, platform-specific artifact pin, digest, publisher evidence, redistribution/operation review, and explicit install choice. Verify before extraction and activation, disallow arbitrary archive entries or lifecycle commands, leave system PATH and existing installs untouched, and handle removal or rollback independently of sign-in.

## Installed vendor CLI and Mandala-owned integration release gate

Source audit: `d0ef87b670ce6c783e10dd9593cda6460a64848c`. Mandatory for claiming that a supported route works with the user's existing installation. This gate is not implemented or passed yet.

- **Installed vendor binary:** Codex and OMP have native app-server/RPC branches in `server/sessions.ts`; Pi uses native RPC in `server/pi.ts` plus our bundled permission extension; Cursor and Antigravity use native streams in `server/local-cli.ts`. Gemini, OpenCode, CodeBuddy, Kimi, DSH and Grok use their same catalog CLI via `server/acp.ts`. None of these 11 routes needs a separately installed ACP launcher. Record exact installed launcher identity; picking a bundled copy or reinstalling the product does not satisfy this gate.
- **Mandala-owned dependency:** Claude currently always launches external `claude-agent-acp` and exposes missing adapters on PATH. Installing Claude Code alone cannot satisfy the current route. Hermes invokes the existing `hermes` command, but its ACP feature may require the upstream extra, depending on distribution. That extra is an integration dependency, not a reason to direct a user to modify their Python environment or reinstall Hermes. OpenClaw's same CLI and Gateway are vendor products; manually adding the separate outbound ACP plugin is not required. Gateway/provider onboarding is different from installing a Mandala integration and must remain a separately reported prerequisite.
- **Packaging:** `scripts/build-desktop.mjs` stages the bundled Node, application backend, CLI resources and Mandala's `server/pi-permission-extension.mjs`; `desktop/electron-builder.cjs` copies the same staging tree for Mac and Windows. Neither stages or registers a Claude ACP launcher or a Hermes ACP extra. The previously checked exact Mac arm64 staged build `62da90a` had only Node in runtime `bin`; the test fixture supplied the 14 launchers, so its green results cannot prove shippable integrations. This is source evidence for the current Windows packaging rule, not an inventory of an exact current Windows installer.
- **UI:** `src/RuntimeSetup.tsx` reports missing Claude ACP, correctly separates most version/connection evidence from a successful turn, links setup guides, and describes Hermes dependencies; it has no Mandala-owned preparation path. Generic PATH errors are not enough: report base CLI absent, installed CLI incompatible, integration dependency unavailable/integrity failure, Gateway/provider setup missing, and real launch failure as separate states. Do not route an integration-only problem to a reinstall or terminal command.

**Claude release hold:** The [official adapter](https://github.com/agentclientprotocol/claude-agent-acp#standalone-executables) defaults to a paired second Claude executable. That is not proof of reuse; its operation/distribution is also separately governed by the [vendor's terms](https://code.claude.com/docs/en/legal-and-compliance). The upstream external-CLI override passes session MCP environment values and headers on the command line. Do not auto-set `CLAUDE_CODE_EXECUTABLE` to the detected CLI, silently fall back to the paired binary, remove user MCP support silently, or duplicate credentials. First qualify a vendor-supported, exact-version integration that binds the selected existing executable and keeps MCP data out of the process command line. Until that passes both platforms, keep the integration explicitly blocked. For Hermes, first prove a version-compatible private dependency plan that does not change the user install; if the vendor distribution's native ACP already works, reuse it unchanged.

**Required fixture/release checks (new, before claiming compliance):**

1. On both platform artifacts, enumerate all 14 catalog routes and check packaged integration manifest and physically present resources. Any route with an app-owned dependency must resolve a pinned bundled or approved app-private artifact, or be reported blocked. Reject a build claim if a required resource is absent, there is no reviewed platform pin, or a status probe silently fixes the state by invoking an installer. The Pi extension existence assertion is a useful precedent, not a comprehensive check.
2. Start a candidate with a fixture representing only the installed vendor CLI, no preinstalled adapter, and competing launcher names outside fixture directories. Assert the intended executable identity and exact argument vector for status and actual first turn, not merely that a response came back. For optional-bridge routes add three independent cases: the already-installed vendor CLI works with the correct private dependency, without a second CLI installation or reinstalling the existing CLI; absent/wrong-digest dependency is reported without a launch/install/network; a previously working native route still works without adding a dependency. Verify both PATH spellings, alternate cwd and a no-fallback missing-command case while preventing registered PATH access. No replacement of vendor binaries, profiles, system PATH, or registry.
3. Use synthetic MCP secret markers for all bridge paths. A separately observed subprocess ledger must show none in argv, logs, URLs or errors; an approved protected transport may receive them. Assert no second vendor binary starts, no unauthorized child or upstream traffic, and a compromised/missing private dependency fails closed without changing the user's working CLI route. Do not enable a real bootstrap, authentication flow or vendor executable to get fixture green.
4. Link the Mac arm64 and Windows x64 package evidence to the exact revision and to separately approved real first-response evidence. Existing `tests/builtin-launcher-binding.test.ts`, `tests/windows-native-launch-conformance.test.ts`, `tests/mandala-ui/runtime-readiness.spec.ts`, and the packaged synthetic harness cover binding, mocked Windows resolution, honest probe display and fixture turns respectively. None proves reuse when a vendor CLI is present but an app-owned integration dependency is absent or corrupted.
